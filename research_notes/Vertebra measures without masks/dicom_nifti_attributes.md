# DICOM header attributes for scale, intensity, geometry and patient covariates, and what NIfTI and dcm2niix keep or lose

Research notes, 2026-10-27. Scope: the attributes a reader needs to set millimetres per pixel at the patient, its uncertainty, Hounsfield units and covariates (sex, age, height, weight) from CT series, single CT slices and single radiographs (CR, DX, fluoroscopy, secondary capture), and what NIfTI-1/2, dcm2niix and nibabel keep.

How the standard's text was obtained: dicom.nema.org refuses plain HTTP clients from this environment, so the exact wording of PS3.3 attribute tables and sections was taken from the innolitics/dicom-standard machine-readable parse of the current web edition of the standard (regenerated monthly by a GitHub Action; [README](https://raw.githubusercontent.com/innolitics/dicom-standard/master/README.md); files [attributes.json](https://raw.githubusercontent.com/innolitics/dicom-standard/master/standard/attributes.json), [module_to_attributes.json](https://raw.githubusercontent.com/innolitics/dicom-standard/master/standard/module_to_attributes.json), [macro_to_attributes.json](https://raw.githubusercontent.com/innolitics/dicom-standard/master/standard/macro_to_attributes.json), [ciod_to_modules.json](https://raw.githubusercontent.com/innolitics/dicom-standard/master/standard/ciod_to_modules.json), [references.json](https://raw.githubusercontent.com/innolitics/dicom-standard/master/standard/references.json)), and checked against dicom.nema.org pages read through a fetch tool (section 10.7, PS3.5 6.2 and 7.4, PS3.15 Annex E, PS3.17 FFF.2.4). Each finding below links the dicom.nema.org section the text belongs to. Pages read on dicom.nema.org on 2026-10-27 were labelled edition 2026c (e.g. [PS3.15 E.3.7](https://dicom.nema.org/medical/dicom/current/output/chtml/part15/sect_E.3.7.html)). Tag, keyword, VR and VM come from the PS3.6 data dictionary as carried in attributes.json.

Requirement types used throughout (PS3.5 section 7.4): Type 1 "shall be included and are mandatory"; "The Length of the Value Field shall not be zero" ([PS3.5 7.4.1](https://dicom.nema.org/medical/dicom/current/output/chtml/part05/sect_7.4.html)). Type 2 "shall be included", but "if a Value for a Type 2 Data Element is unknown it can be encoded with zero Value Length and no Value" ([PS3.5 7.4.3](https://dicom.nema.org/medical/dicom/current/output/chtml/part05/sect_7.4.3.html)). Type 3 is optional and "Absence of a Type 3 Data Element from a Data Set does not convey any significance"; "The meaning of a zero length Type 3 Data Element shall be precisely the same as that Data Element being absent" ([PS3.5 7.4.5](https://dicom.nema.org/medical/dicom/current/output/chtml/part05/sect_7.4.5.html)). 1C and 2C are the conditional forms, with the condition written in each attribute's description (quoted below). A module's usage in an IOD is M (mandatory), C (conditional) or U (user optional); an attribute's type only binds when its module is present.

## Pixel Spacing (0028,0030) versus Imager Pixel Spacing (0018,1164) versus Nominal Scanned Pixel Spacing (0018,2010) on projection radiographs; Pixel Spacing Calibration Type (0028,0A02) and Description (0028,0A04)

### Takeaway
On projection images Imager Pixel Spacing is at the front plane of the detector housing and is never corrected for magnification; Pixel Spacing is defined as "in the Patient" and, when it differs from Imager Pixel Spacing (or Nominal Scanned Pixel Spacing for digitized film), the image has been corrected for geometric magnification (GEOMETRY) or calibrated against a fiducial (FIDUCIAL), each valid only near the central ray at one depth. When Pixel Spacing equals Imager Pixel Spacing, or Calibration Type is absent, the reader must assume detector-plane scale (an overestimate of patient size by the magnification factor), and when all three of Pixel Spacing Calibration Type, Imager Pixel Spacing and Nominal Scanned Pixel Spacing are absent the standard says it "cannot be determined whether or not correction or calibration have been performed."

How viewers act on these attributes (implementation evidence, not the standard):
- Cornerstone3D (`calculateRadiographicPixelSpacing`) applies only to a list of projection SOP classes (CR 1.2.840.10008.5.1.4.1.1.1, DX 1.2.840.10008.5.1.4.1.1.1.1 and .1.1.1.1, mammography, intra-oral, XA 1.2.840.10008.5.1.4.1.1.12.1, Enhanced XA, XRF 1.2.840.10008.5.1.4.1.1.12.2, Enhanced XRF). Non-projection SOP classes get NOT_APPLICABLE. — [Cornerstone3D getPixelSpacingInformation.ts](https://raw.githubusercontent.com/cornerstonejs/cornerstone3D/main/packages/metadata/src/utilities/getPixelSpacingInformation.ts)
- InteleViewer calls Imager Pixel Spacing "the most reliable value for calibrating measurements", treats it as valid only if greater than Pixel Spacing when both are present, and displays one of: "Measurements not calibrated." (no IPS, no PS); "Measurements corrected at modality." (valid IPS, PS present, no ERMF); "Measurements not corrected. Measured size is at detector." (valid IPS, no PS, no ERMF); "Measurements corrected using the ERMF (mag factor)." (valid IPS and ERMF); "Measurements are uncertain."; "Measurements are user calibrated." — [InteleViewer: Measurement Calibration for Projection Radiographic Images](https://inteleviewer.documentation.intelerad.com/iv-help/PACS-5-4-1-P2/en/Content/Topics/IV_Measurement_Calibration.html)

### Inferences
- A reader's decision rule that follows the standard: (1) if Pixel Spacing Calibration Type is FIDUCIAL, use Pixel Spacing as valid at the fiducial's depth near the central ray; (2) if GEOMETRY, use Pixel Spacing as valid at an "unspecified depth"; (3) if Imager Pixel Spacing is present and Pixel Spacing differs from it with no Calibration Type, the image was corrected or calibrated in an unknown way (record as "corrected, method unknown"); (4) if Pixel Spacing equals Imager Pixel Spacing, or only Imager Pixel Spacing is present, scale is at the detector and must be divided by a magnification factor (from ERMF or SID/SOD, next section) to approach patient scale; (5) if only Pixel Spacing is present on a CR or SC image with neither Imager nor Nominal Scanned Pixel Spacing and no Calibration Type, provenance is undeterminable (10.7.1.1) and the uncertainty must be wide.
- Because CR makes Imager Pixel Spacing only Type 3 while DX makes it Type 1, CR files are the ones most likely to land in case (5).
- The Image Plane module's Pixel Spacing (CT, MR) is a reconstruction-grid spacing and has no magnification ambiguity; the calibration logic above applies only to projection and secondary-capture IODs.
- InteleViewer's paraphrase of ERMF as "source-to-patient distance to source-to-detector distance" is the inverse of the standard's SID/SOD (next section); a reader must use the standard's definition (ERMF >= 1, divide detector spacing by it), as Cornerstone does.

### Gaps
- No survey was found of how often clinical CR/DX files carry Pixel Spacing different from Imager Pixel Spacing, or Calibration Type, by vendor; measuring this on the project's own corpora would close it.
- The DICOM CP that introduced Pixel Spacing Calibration Type (the request named CP 586 or similar) was not retrieved; dicom.nema.org's CP index could not be read from this environment, so its number and date are unverified.

## Estimated Radiographic Magnification Factor (0018,1114), Distance Source to Detector (0018,1110), Distance Source to Patient (0018,1111), Distance Source to Isocenter (0018,9402), Table Height (0018,1130); magnification = SID/SOD; IHE and measurement guidance; typical values

### Takeaway
The standard defines Estimated Radiographic Magnification Factor as SID/SOD, so patient-plane spacing = Imager Pixel Spacing / ERMF; all of ERMF, SID and SOD are Type 3 in CR and DX, and in DX the SOD is deliberately the distance to the table or bucky surface, not to any point in the patient, so SID/SOD underestimates the magnification of a vertebra that sits some centimetres above the table. Enhanced XA/XRF can carry a per-frame Object Pixel Spacing in Center of Beam computed from Distance Source to Isocenter and Distance Object to Table Top, which is the closest the standard comes to a patient-plane scale for fluoroscopy.

### Inferences
- For a lumbar spine radiograph the vertebral body sits roughly 10 to 15 cm above the table top for an AP view (more for a lateral at mid-coronal plane). With a 1000 mm SID and the DX definition of SOD (to the bucky surface), SID/SOD is close to 1.0 to 1.1, whereas the true magnification of the vertebra is SID/(SOD - depth), larger by several percent; this is an order-of-magnitude estimate from the geometry above, not a cited figure, and should be stated as an assumption in any uncertainty budget.
- An uncertainty model can therefore treat ERMF-corrected spacing as biased large (underestimating magnification) by an unknown patient-depth term, and detector-plane spacing (no ERMF) as biased large by the full magnification (typically several to 20 percent for spine views; again an inference to be checked on the project's own data).
- For fluoroscopy (C-arm), the XRF IOD uses the X-Ray Acquisition module (Imager Pixel Spacing Type 3) and the XRF Positioner (ERMF, SID, SOD Type 3, SOD to "center of field of view"), so on a C-arm the SOD is to the isocenter rather than to the table; the reader must branch on SOP class / module when interpreting SOD.
- A reader should prefer, in order: Object Pixel Spacing in Center of Beam (Enhanced XA/XRF, per frame); Pixel Spacing with FIDUCIAL; Pixel Spacing with GEOMETRY; Imager Pixel Spacing / ERMF; Imager Pixel Spacing / (SID/SOD); Imager Pixel Spacing alone (detector plane); Pixel Spacing of undeterminable provenance. This ordering is a design inference from the definitions above.

### Gaps
- No published survey of typical stored ERMF, SID or SOD values for spine radiography or C-arm fluoroscopy was found; the IHE Radiology Basic Image Review (BIR) supplement, which specifies how a viewer labels calibrated measurements, appeared in search results ([Australian Digital Health mirror](https://implementer.digitalhealth.gov.au/standards/ihe-radiology-technical-framework-supplement-basic-image-review-bir-v1-3)) but its text was not read here.
- The CP that clarified projection pixel spacing could not be read (dicom.nema.org CP pages not reachable by script here).

## CT: Rescale Slope (0028,1053), Rescale Intercept (0028,1052), Rescale Type (0028,1054), Pixel Spacing, Slice Thickness (0018,0050), Spacing Between Slices (0018,0088), Image Position (Patient) (0020,0032), Image Orientation (Patient) (0020,0037); slice sorting and the affine; Enhanced CT functional groups; KVP, Convolution Kernel, Gantry/Detector Tilt

### Takeaway
HU = Rescale Slope x stored value + Rescale Intercept, and in a CT Image whose Image Type Value 1 is ORIGINAL and Value 3 is not LOCALIZER (and not multi-energy) the output "shall be" HU even when Rescale Type is absent. Geometry comes from Image Position (Patient), Image Orientation (Patient) and Pixel Spacing per slice; the slice step must be computed from the positions projected on the slice normal, not from Slice Thickness (nominal) or Spacing Between Slices (Type 3, sometimes misused). In Enhanced CT the same attributes move into the Pixel Measures, Plane Position, Plane Orientation and CT Pixel Value Transformation functional groups, shared or per frame. Gantry/Detector Tilt is "Not intended for mathematical computations"; a tilted acquisition shows up as slice positions that do not lie along the row x column normal.

### Inferences
- Slice sorting recipe consistent with the standard and with nibabel: compute n = row_cosine x column_cosine from IOP (check all slices share IOP within tolerance), compute d_k = n . IPP_k for every slice, sort by d_k, take the step as the median of successive differences, and flag the series if the steps vary (dcm2niix refuses such volumes, below) or if (IPP_last - IPP_first) is not parallel to n (gantry tilt or shear). Never sort by Instance Number or Slice Location.
- Voxel size for vertebral measurement: in-plane from Pixel Spacing (row spacing first), through-plane from the computed step, never from Slice Thickness; Slice Thickness is still a covariate for partial-volume blur.
- HU: apply Slope and Intercept to every slice separately (they may differ per slice); treat Rescale Type absent in a CT Image with ORIGINAL and not LOCALIZER as HU; treat LOCALIZER images (scout) as projection images and exclude them from volumes.
- A localizer (CT Image IOD, Image Type Value 3 LOCALIZER) has Image Plane geometry but is a projection; its Pixel Spacing has the same magnification ambiguity as a radiograph.

### Gaps
- PS3.3 does not define, in the text read, how Gantry/Detector Tilt sign maps onto the IPP shear for all vendors; dcm2niix's code comments (next section) describe a sign reversal found empirically.

## NIfTI-1 and NIfTI-2: what the header keeps and loses; dcm2niix's BIDS sidecar and its handling of rescale; nibabel's scl_slope and affine; LPS versus RAS

### Takeaway
NIfTI keeps one grid (dim, pixdim), two affines (qform with its quaternion and qfac in pixdim[0], and sform), one linear scaling (scl_slope, scl_inter) and units (xyzt_units); it has no field for any patient attribute, Rescale Type, pixel spacing calibration type, magnification, kVp or kernel. Its world space is RAS+ while DICOM's is LPS+, so x and y flip sign. dcm2niix writes the stored integers and copies Rescale Slope and Intercept into scl_slope and scl_inter (it does not bake HU into the voxels), sets qform_code = sform_code = 1 (scanner anatomical), and by default (-ba y) omits PatientSex, PatientAge, PatientSize and PatientWeight from the JSON sidecar. nibabel's get_fdata() applies the scaling and marks the header's scl fields as consumed (NaN) on load.

### Cited Findings
NIfTI-1 header (nifti1.h, public domain):
- Scaling: "If the scl_slope field is nonzero, then each voxel value in the dataset should be scaled as y = scl_slope * x + scl_inter where x = voxel value stored y = "true" voxel value"; "it is legal to use scaling even if the datatype is a float type"; "the scaling is to be ignored if datatype is DT_RGB24." — [nifti1.h](https://raw.githubusercontent.com/NIFTI-Imaging/nifti_clib/master/niftilib/nifti1.h)
- World coordinates: "The (x,y,z) coordinates refer to the CENTER of a voxel. In methods 2 and 3, the (x,y,z) axes refer to a subject-based coordinate system, with +x = Right +y = Anterior +z = Superior. nibabel:
- Affine choice (`get_best_affine()`): "If sform_code != 0 ('unknown') use the sform affine; else If qform_code != 0 ('unknown') use the qform affine; else Use the fall-back affine." — [nibabel nifti_images.rst](https://raw.githubusercontent.com/nipy/nibabel/master/doc/source/nifti_images.rst)
- Scaling: "By default, nibabel will take care of this scaling for you"; data = stored x scl_slope + scl_inter "if both of scl_slope and scl_inter are defined"; "When you load an image, the header scaling values automatically get set to NaN (undefined) to mark the fact that the scaling values have been consumed by the read"; slope and intercept are read with `header.get_slope_inter()` and set with `set_slope_inter()`; `get_fdata()` returns the scaled floating-point array. — [nibabel nifti_images.rst](https://raw.githubusercontent.com/nipy/nibabel/master/doc/source/nifti_images.rst); [nibabel images_and_memory.rst](https://raw.githubusercontent.com/nipy/nibabel/master/doc/source/images_and_memory.rst)
- nibabel calls its convention "RAS+", "meaning that Right, Anterior, Superior are all positive"; it quotes DICOM's LPS axes from C.7.6.2.1.1 and derives the DICOM affine (including the row/column transpose of pixel indices). — [nibabel coordinate_systems.rst](https://raw.githubusercontent.com/nipy/nibabel/master/doc/source/coordinate_systems.rst); [nibabel dicom_orientation.rst](https://raw.githubusercontent.com/nipy/nibabel/master/doc/source/dicom/dicom_orientation.rst)

### Inferences
- LPS to RAS: affine_RAS = diag(-1, -1, 1, 1) . affine_LPS, i.e. negate the first two rows of the DICOM-derived affine; the voxel array is unchanged. This follows directly from DICOM's +x left, +y posterior and NIfTI's +x right, +y anterior quoted above.
- Pixel index order: DICOM's equation takes (i = column, j = row); NumPy arrays from pydicom are indexed [row, column], so the affine built for array indices must swap the first two columns (nibabel's "ij-transpose"). Getting this wrong swaps row and column spacing on non-square pixels.
- Everything a measurement pipeline needs beyond grid geometry and HU (sex, age, size, weight, kVp, kernel, calibration type, magnification, view) must travel in a sidecar; with dcm2niix's default -ba y the patient covariates are lost, so conversions for covariate work must use -ba n (or -ba o) under the project's data agreement, or read the DICOM directly.
- A NIfTI from a projection radiograph (dcm2niix "CR") carries pixdim taken from Pixel Spacing with no record of whether that was detector-plane or corrected; such NIfTIs cannot be scaled reliably without the original DICOM.
- Because scl_slope = 0 means "no scaling" in NIfTI, a reader must treat slope 0 (and NaN, nibabel's consumed marker) as 1 with intercept 0.

### Gaps
- Which DICOM element dcm2niix uses for pixdim on CR/DX (Pixel Spacing versus Imager Pixel Spacing) was not traced in the source; it should be checked on a sample file before trusting a converted radiograph.

## Single DICOM files: telling a lone CT slice from a projection radiograph; secondary capture without valid spacing

### Takeaway
Decide by SOP Class UID first (CT Image 1.2.840.10008.5.1.4.1.1.2, Enhanced CT .2.1, CR .1, DX .1.1 and .1.1.1, XRF .12.2, XA .12.1, SC .7 and multi-frame SC .7.1 to .7.4), then Modality, then Image Type (CT Value 3 AXIAL versus LOCALIZER). A CT slice has the mandatory Image Plane module (IPP, IOP, Pixel Spacing Type 1); a CR/DX image has no Image Plane module and its scale semantics are those of the first section. Secondary capture images have Pixel Spacing only if "calibrated", their Modality is Type 3 and describes the original equipment, and an Image Plane module is optional, so their spacing should be treated as absent unless Pixel Spacing is present with a calibration story.

### Cited Findings
- SOP Class UIDs: Computed Radiography Image Storage 1.2.840.10008.5.1.4.1.1.1; Digital X-Ray Image Storage For Presentation 1.2.840.10008.5.1.4.1.1.1.1 and For Processing 1.2.840.10008.5.1.4.1.1.1.1.1; CT Image Storage 1.2.840.10008.5.1.4.1.1.2; Enhanced CT Image Storage 1.2.840.10008.5.1.4.1.1.2.1; Secondary Capture Image Storage 1.2.840.10008.5.1.4.1.1.7; Multi-frame Single Bit, Grayscale Byte, Grayscale Word and True Color Secondary Capture 1.2.840.10008.5.1.4.1.1.7.1 to .7.4; X-Ray Angiographic 1.2.840.10008.5.1.4.1.1.12.1; X-Ray Radiofluoroscopic 1.2.840.10008.5.1.4.1.1.12.2. — [pydicom _uid_dict.py](https://raw.githubusercontent.com/pydicom/pydicom/main/src/pydicom/_uid_dict.py)

### Inferences
- Classification rule for a lone file: SOP Class in {CT Image, Enhanced CT} and Image Type Value 3 not LOCALIZER -> tomographic slice (scale exact from Pixel Spacing; through-plane step unknown unless Spacing Between Slices is present, Clunie's "report only area" case); CT LOCALIZER -> projection; SOP Class in {CR, DX, XRF, XA} -> projection (use the first two sections); SOP Class in SC family -> inspect Conversion Type: DF with Nominal Scanned Pixel Spacing gives spacing on the film (itself at the film's magnification), WSD/DV/DI usually means a screenshot or video grab whose spacing is meaningless unless Pixel Spacing is present with a calibration type.
- A screenshot SC of a CT or radiograph whose Pixel Spacing was copied from the source is still suspect, because the capture may be resized; absence of Pixel Spacing in SC must be read as "unknown scale", never as 1 mm.

### Gaps
- No source quantified how often exported or SC radiographs carry Pixel Spacing at all.

## PNG and JPEG: metadata that can carry physical scale, and why it is unreliable for medical scale

### Takeaway
PNG's pHYs chunk can state pixels per metre (unit 1) or only an aspect ratio (unit 0); JFIF's APP0 can state pixels per inch or per centimetre, or only an aspect ratio; EXIF stores XResolution/YResolution with a ResolutionUnit and designates 72 dpi when resolution is unknown. None of these is defined at the patient or detector, they describe intended print or display size, and exporters commonly write defaults, so they must never set a vertebral measurement's scale.

### Cited Findings
- PNG pHYs (PNG Third Edition, W3C Recommendation 24 June 2025, section 11.3.4.3): "The pHYs chunk specifies the intended pixel size or aspect ratio for display of the image." Fields: Pixels per unit, X axis (4 bytes unsigned); Pixels per unit, Y axis (4 bytes); Unit specifier (1 byte): 0 "unit is unknown", 1 "unit is the metre". "When the unit specifier is 0, the pHYs chunk defines pixel aspect ratio only; the actual size of the pixels remains unspecified. If the pHYs chunk is not present, pixels are assumed to be square, and the physical size of each pixel is unspecified." — [PNG spec 11.3.4.3](https://www.w3.org/TR/png-3/#11pHYs); text read from the [W3C PNG spec source](https://raw.githubusercontent.com/w3c/png/main/index.html)
- JFIF APP0 (ITU-T T.871 / ISO/IEC 10918-5): Density units 1 byte: 00 no units (pixel aspect ratio Ydensity:Xdensity), 01 pixels per inch, 02 pixels per centimetre; Xdensity and Ydensity 2 bytes each, "must not be zero"; JFIF and Exif are mutually incompatible because each requires its segment to follow SOI. — [Wikipedia: JPEG File Interchange Format](https://en.wikipedia.org/wiki/JPEG_File_Interchange_Format)
- EXIF XResolution: "the number of pixels per ResolutionUnit in the ImageWidth direction. When the image resolution is unknown, 72 [dpi] is designated." (secondary source quoting the Exif tag description). — [FreeImage.NET documentation, XResolution](https://freeimage.sourceforge.io/fnet/html/BD344C00.htm)

### Inferences
- Even a correct pHYs or JFIF density on an exported radiograph would at best equal the DICOM Pixel Spacing or Imager Pixel Spacing at export time, without the calibration type, magnification or resizing history; a 72 dpi or 96 dpi value is a default, not a measurement. A reader should log these values as provenance and ignore them for scale, falling back to an in-image reference (ruler, known implant, or anatomical prior) with wide uncertainty.

### Gaps
- The Exif specification itself (CIPA DC-008) was not read; the 72 dpi rule is cited from a secondary library document.

## Pure-Python readers and their licences

### Takeaway
